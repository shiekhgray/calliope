## Session 1 — Loose FLAC single import

### Shipped
Support for importing Qobuz singles, which are sold as bare `.flac` files (no zip,
no folder structure). Committed + pushed to master as `b9f5cca`.

Three layers changed:

1. **Host script** (`scripts/qobuz_import.py`) — added a `--loose <track.flac> [cover.jpg]`
   mode. Mirrors `amazon_import.py`'s loose path (reads albumartist/album/title tags via
   mutagen, resolves primary artist from collaboration tags, optional cover→Folder.jpg)
   but combines it with the existing FLAC→MP3 V0 transcode. `main()` was restructured:
   positional arg renamed `zips`→`files`, added `--loose` flag + routing. Album-zip path
   unchanged.

2. **Web upload** (`api/app/routers/import_music.py`) — `.flac` previously fell through to
   the zip handler and failed ("Not a valid zip file"). Now `.flac` routes to
   `_process_audio_single`, which transcodes FLAC→MP3 (temp file + ffmpeg) before writing.
   Added `LOOSE_SINGLE_EXTENSIONS` constant. `_process_audio_single` now also uses
   `Path(filename).name` (path-traversal hardening) instead of raw filename.

3. **Frontend** (`web/src/pages/ImportPage.jsx`) — added `.flac` to the accept regex,
   error message, `<input accept>`, and dropzone sub-label.

### Auto-tagging singles as 'single'
The owner asked that `--loose` imports automatically get `album_type='single'`. Since the
host script (runs on host, no DB access) and the scanner (runs in container) only share the
filesystem, the chosen mechanism is a **hidden `.album_type` marker file** dropped in the
album dir containing `single`.

- `api/scripts/scan.py`: new `read_album_type(album_dir)` helper + `ALBUM_TYPE_MARKER` /
  `VALID_ALBUM_TYPES` constants. `upsert_album` gained an `album_type` param applied
  **only on album creation** — a rescan never clobbers a later manual change via
  PATCH /albums/{id}/type (the AlbumPage type-cycle pill).
- Both the host `--loose` path and the web `_process_audio_single` path drop the marker.
- Marker has an empty filename suffix (`Path(".album_type").suffix == ""`), so the scanner's
  track loop (filters by AUDIO_EXTENSIONS) and `find_cover_art` (filters by `.jpg`) both
  ignore it — verified before relying on it.

### Key decisions
- **Transcode FLAC→MP3 rather than store lossless.** Matches how the rest of the library is
  stored; the no-transcode constraint in CLAUDE.md is about *streaming*, not import. Flagged
  to owner as reversible if they ever want lossless singles (scanner already supports .flac).
- **All loose singles get the marker, not just FLAC.** A loose `.mp3`/`.m4a` uploaded via web
  now also tags `single` (previously came in as `album`). Done for consistency with the host
  `--loose` convention and to avoid "flac singles tagged, mp3 singles not." Flagged to owner;
  offered to gate to FLAC-only if undesired — no objection given.
- Marker applies on creation only → existing library albums are unaffected; only future
  imports change.

### Gotchas discovered
- The web `/import/upload` path is **completely separate** from the host `qobuz_import.py`
  script. Supporting FLAC in one does nothing for the other — both had to be changed.
- `qobuz_import.py` `main()` bails if `--music-root` doesn't already exist, so the throwaway
  test needed `mkdir -p` on the lib dir first (the real `/backup/calliope/music` always exists).

  — `scan.py` and `import_music.py` are baked into the image. No migration needed (`album_type`
  already exists from migration 0009).
- No nginx/DB schema changes.

### Verified

- Web upload: logged in as clippy, POSTed a real FLAC to `/import/upload` → `status: ok`,

## Session 2 — Radio Modes v1

### Shipped
Selectable radio continuation algorithms (`prd/radio-modes.md`), replacing the implicit
Classic-only random walk. v1 = the four modes + Variety; Phase 2 cluster-fencing deferred
as planned. Committed on a new `radio` branch as `6e8872b` (not pushed).

**Backend:**
- **Migration 0014** (`0014_add_radio_settings.py`) — `radio_mode VARCHAR(16) DEFAULT
  'classic'` + `radio_variety INTEGER DEFAULT 0` on `users`. **Applied to prod DB.**
- **`api/app/similarity.py`** (new) — factored the canonical `DIM_SLICES` + the
  z-score → per-user weights → L2-normalize pipeline (`load_weighted_matrix`) + track
  enrichment (`enrich_tracks`) into one shared module. `/tracks/{id}/similar` refactored
  onto it (deleted its duplicate `DIM_SLICES` + inline pipeline). `albums.py` (no weights)
  and `map.py` (float64 + KMeans + `w=` override) keep their specialized copies.
- **`api/app/routers/radio.py`** (new) — `POST /radio/next`. Mode-agnostic, **stateless**:
  the client owns session state (mode/anchor_id/last_id/played_ids/radius/source_album_id/
  variety) and passes it in; server returns one enriched track + updated radius, or `204`
  when no candidate remains. Implements classic / anchor / ripple / anchored_ripple +
  top-K Variety sampling. Registered in `main.py`.
- **`auth.py`** — `PUT /auth/radio-settings` (partial, validated: mode enum + variety
  0–10); `radio_mode`/`radio_variety` added to `_user_response` (so `GET /auth/me` carries
  them).

**Web (HMR, no rebuild):**
- **`RadioModesModal.jsx`** (new) — 4-mode radio group with plain-language copy + a Variety
  slider; modeled on `SimilarityWeightsModal`. Wired into the user menu as "Radio Modes"
  (next to "Sound Matching") in `Layout.jsx`. CSS added to `index.css` (`.radio-mode-*`).
- **`PlayerContext.jsx`** — `_extendWithRadio` now POSTs `/radio/next` instead of
  `/tracks/{id}/similar`. New refs: `anchorRef` (track that started the station, pinned on
  the first extension after a manual play), `sourceAlbumRef`, `radiusRef` (ripple state
  echoed to/from server) — all reset in `playTrack`. Mode + variety read from `['me']` via
  `useQuery`, mirrored into `radioAlgoRef`/`radioVarietyRef` so the non-reactive
  onended/_extendWithRadio handlers can read them. The on/off toggle (localStorage) is
  unchanged.

### Key decisions
- **Migration numbered 0014, not 0013** as the PRD text said — 0013 was already taken by
  Music Map. (`.todo` already flagged this.)
- **Math moved server-side into one endpoint.** The client has no raw vectors, and the new
  modes need query-by-computed-vector (midpoints) + distance values (ripple radius), which
  `/tracks/{id}/similar` (ranked-list-only, track-id-keyed) can't give. One mode-agnostic
  `/radio/next` keeps all weighting consistent with Sound Matching.
- **Cohesion cap = 25th percentile of the just-played track's distances** to all candidates
  (admits the closest ~quartile), relaxed (dropped) if it empties rather than stopping
  radio. Chosen over the PRD's "75th-pct of global nearest-neighbour distances" because the
  latter is O(N²) per call and yields a tiny cap that admits almost nothing but exact dupes.
  This is cheap (one vector·matrix) and adaptive. **`COHESION_PERCENTILE=25` and
  `SOFT_RADIUS_STEP=0.5` are guesses — flagged as needing real-library tuning.**
- **`source_album_id` carries the kickoff-album exclusion** (instead of re-excluding the
  current track's album each hop, as the old code did). Set once on the first extension.
- **Left `albums.py`/`map.py` DIM_SLICES copies alone.** Only tracks+radio share the helper;
  `albums` genre-suggest applies *no* weights and `map` needs float64 — refactoring them
  would change behavior for no benefit to this feature.

### Gotchas discovered
- `PlayerContext` could subscribe to `['me']` only because `QueryClientProvider` wraps

- Vite logs "Could not Fast Refresh (usePlayer export incompatible)" on every
  `PlayerContext` edit — **benign**, it just forces a full page reload (the module exports
  both a component and a hook). Not an error.
- Smoke tests showed repeated "Je veux te voir" results — that's the known mp3/m4a duplicate
  tracks surfacing because raw curl tests didn't pass `source_album_id`; the client always
  does. Not a bug.
