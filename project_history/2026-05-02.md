## Session 1 — Android Playlist Screens

### What shipped

**Playlist screens — full implementation (14 files, 864 insertions)**

New files:
- `data/api/model/PlaylistModels.kt` — `Playlist`, `PlaylistEntry`, `PlaylistDetail`, `CreatePlaylistRequest`, `AddTrackRequest`, `ReorderRequest` (Moshi `@JsonClass` annotated, matching exact API field names)

- `ui/playlist/PlaylistDetailScreen.kt` — track list, edit mode (▲▼✕ per row), delete confirm, "add to another playlist" sheet
- `ui/common/AddToPlaylistViewModel.kt` — fetchPlaylists + addTrack (suspend)
- `ui/common/AddToPlaylistSheet.kt` — `ModalBottomSheet` listing all playlists; Toast on success

Modified files:
- `CalliopeApi.kt` — 7 new endpoints: GET/POST playlists, GET/POST/DELETE/PUT playlist detail and tracks
- `TrackRow.kt` — added optional `onAddToPlaylist: (() -> Unit)?` and `onRemove: (() -> Unit)?` trailing icon buttons (null = hidden, backward compatible)
- `MainScreen.kt` — replaced Playlists placeholder with `PlaylistListScreen`; added `onNavigateToPlaylist` param
- `NavGraph.kt` — added `playlist/{playlistId}` route for `PlaylistDetailScreen`
- `AlbumScreen.kt`, `ArtistScreen.kt`, `SearchScreen.kt` — "add to playlist" icon on each TrackRow; `AddToPlaylistSheet` shown when a track is selected

### Key decisions

- **Edit mode toggle** for reorder/remove in PlaylistDetailScreen rather than always-visible controls. Keeps normal playback view clean; ▲▼ buttons are simpler than drag-to-reorder and avoid needing a third-party library.
- **Delete with confirm dialog** instead of swipe-to-delete. Avoids accidental destruction of playlists; `SwipeToDismissBox` complexity not worth it for a low-frequency action.
- **`AddToPlaylistViewModel` in `ui/common/`** scoped to the nav back stack entry, not shared. Each screen gets its own instance that fetches playlists fresh when the sheet opens. Simple and avoids shared-state complexity.
- **`onRemove` param on `TrackRow`** added but not used by PlaylistDetailScreen (which uses its own `EditableTrackRow` in edit mode). Available for future use.
- **Toast for "Added to [playlist]"** feedback — simpler than wiring a `SnackbarHostState` through multiple screens.

### API shape confirmed

`GET /playlists/{id}` response uses key `entries` (not `tracks`), each entry has `{id, position, track: {...}}`. Track inside entries has all fields except `play_count` (defaults to 0 via Moshi default).

`DELETE /playlists/{id}/tracks/{track_id}` — the path param is the **track's ID**, not the playlist_track entry ID.

All changes are Android-only. No migrations, no API server changes, no nginx changes.

## Session 2 — WorkManager Playlist Downloads + Room DB

### What shipped

**Offline downloads — full implementation (9 files, ~450 insertions)**

New files:
- `data/db/DownloadStatus.kt` — enum: PENDING, DOWNLOADING, DONE, FAILED
- `data/db/DownloadedTrack.kt` — Room entity, composite PK `(playlist_id, track_id)`
- `data/db/DownloadedTrackDao.kt` — observeByPlaylist (Flow), findDoneByTrackId, upsert, deleteByPlaylist, updateStatus
- `data/db/CalliopeDatabase.kt` — Room database + `DownloadStatusConverter` TypeConverter
- `di/DatabaseModule.kt` — provides `CalliopeDatabase`, `DownloadedTrackDao`, `WorkManager`
- `work/DownloadPlaylistWorker.kt` — `@HiltWorker` CoroutineWorker; downloads all tracks in a playlist via OkHttp, updates Room per-track, resumes on retry (skips DONE tracks), shows foreground notification

Modified files:
- `App.kt` — implements `Configuration.Provider` to supply `HiltWorkerFactory`; creates the `calliope_downloads` NotificationChannel
- `AndroidManifest.xml` — adds `FOREGROUND_SERVICE_DATA_SYNC` permission; merges `foregroundServiceType="dataSync"` on WorkManager's `SystemForegroundService`; removes default `WorkManagerInitializer` so Hilt factory takes effect
- `gradle/libs.versions.toml` + `app/build.gradle.kts` — adds `androidx.hilt:hilt-work` + `androidx.hilt:hilt-compiler` (both on version `1.2.0`)
- `playback/PlayerViewModel.kt` — injects `DownloadedTrackDao`; `playQueue` now suspends into a coroutine to look up local file for each track before building `MediaItem`; `toMediaItem()` accepts optional `localFilePath` and uses `Uri.fromFile()` when a DONE file exists
- `ui/playlist/PlaylistDetailViewModel.kt` — injects `DownloadedTrackDao`, `WorkManager`, `@ApplicationContext`; exposes `downloadedTrackIds: StateFlow<Set<Int>>` and `downloadUiState: StateFlow<DownloadUiState>`; adds `startDownload()`, `cancelDownload()`
- `ui/playlist/PlaylistDetailScreen.kt` — TopAppBar download button (Idle → start / InProgress → cancel with spinner / Complete → cloud-done icon); per-track `isDownloaded` passed to `TrackRow`
- `ui/common/TrackRow.kt` — adds optional `isDownloaded: Boolean = false`; shows 16dp `DownloadDone` icon in primary color when true

### Key decisions

- **OkHttpClient reuse in worker**: the injected `OkHttpClient` already carries `AuthInterceptor`, so download requests automatically get the Bearer token — no manual header injection needed in the worker.
- **Track-ID-only lookup for playback**: `findDoneByTrackId` ignores playlist context so any DONE file (from any playlist download) is usable for playback.
- **3-arg `ForegroundInfo`** with `FOREGROUND_SERVICE_TYPE_DATA_SYNC`: required on API 34+; safe on API 26-28 because the constant is inlined as an int at compile time.
- **`ExistingWorkPolicy.KEEP`**: re-tapping download on an already-queued playlist is a no-op. Worker is inherently resumable (skips DONE tracks).
- **Cancel deletes files and DB rows**: `cancelDownload` cancels the WorkManager tag, deletes all downloaded files for the playlist, and clears the DB rows for that playlist — clean slate.
- **`DownloadUiState.Idle`** means nothing downloaded and nothing running. Even a partial/failed download shows `Idle` after cancel, so the user can simply tap again.

### No API/infra changes

All changes are Android-only. No server migrations, no nginx changes.
