## Session 1 — Android Download Playback Bug Fixes

### What shipped

**2 files changed (commit a331f1f on master)**

- `playback/MusicService.kt` — replaced `DefaultHttpDataSource.Factory` with `DefaultDataSource.Factory(context, httpFactory)`. The HTTP factory is now the fallback for network URIs; local `file://` URIs route through `DefaultDataSource` which handles them natively.
- `playback/PlayerViewModel.kt` — `playQueue()` now launches a coroutine that checks `downloadedTrackDao.findDoneByTrackId()` for every track before evaluating the WiFi guard. If all tracks exist locally, the guard is bypassed entirely.

### Bugs fixed

**Downloaded tracks unplayable from playlist page**

Root cause: `MusicService` wired `DefaultHttpDataSource.Factory` directly as the ExoPlayer data source factory. This factory only resolves `http://` and `https://` schemes. `PlayerViewModel.executePlay()` correctly looked up local file paths from Room and called `Uri.fromFile()`, but when ExoPlayer received those `file://` URIs it couldn't open them — the factory had no handler for the scheme, causing silent playback failure.

Fix: wrap with `DefaultDataSource.Factory(context, httpFactory)`. Routes `file://`/`content://` locally, delegates everything else to the HTTP factory (auth headers still apply to network requests).

**Spurious WiFi warning for downloaded playlists**

Root cause: `playQueue()` checked `isOnWifi()` before consulting Room, so even a fully-downloaded playlist showed the "You're on mobile data" dialog on cellular.

Fix: query Room first (all in one coroutine); skip the WiFi guard if every track resolves to an existing local file. Mixed playlists (some downloaded, some not) still warn — correct, since they need to stream the missing tracks.

### Key decisions

- **Check all-or-nothing for the WiFi guard** — if even one track in the list needs streaming, the warning still fires. Safer than silently streaming on cellular when the user might not realize it.
- **`playQueue` stays non-suspend (public API unchanged)** — wrapping in `viewModelScope.launch` keeps callers in all screens unchanged. The DB check is a handful of fast Room reads; no perceptible delay before playback starts.

### No API/infra changes

Android-only. No migrations, no server changes, no nginx changes.

**Android Auto PRD (`prd/android-auto.md`)**

New PRD written covering the full Auto implementation. Key decisions:

- **Browse tree (Option B)**: Artists → Artist → [▶ Top Tracks folder + Album nodes] → Tracks. Artist detail level retained so top tracks (sorted by play_count) are accessible without navigating into an album. More taps for album browsing but exposes the most-loved tracks directly.
- **Node IDs encode context**: e.g. `track/{id}/album/{albumId}` vs `track/{id}/playlist/{playlistId}`. Lets `onPlayFromMediaId` load the correct sibling queue without an extra lookup call.
- **Queue building**: tapping any track enqueues the full context (rest of album/playlist/top-tracks/recently-played) from that position.
- **Radio mode in Auto**: toggle button (`CommandButton` in session `customLayout`) on the Auto Now Playing card, **default ON**. When queue runs out, auto-extends via `GET /tracks/{id}/similar`. Mirrors phone behaviour but defaults to on so the car never goes silent.
- **`RadioQueueExtender` refactor**: radio logic currently in `PlayerViewModel` needs extracting into a shared injectable used by both `PlayerViewModel` and `MusicService`.
- **Recently Played**: flat list of tracks sorted by `play_count` desc, limit 50. No new timestamp column needed.
- **Two new API endpoints needed**: `GET /artists/{id}/tracks?sort=play_count&limit=N` and `GET /tracks?sort=play_count&limit=N`.
- **In-car search and voice deferred**: out of scope for this pass.
- **Add to playlist in Auto**: out of scope (no free-form picker possible within Auto UI constraints).

Planning only. No migrations, no server changes, no API rebuild.

## Session 3 — Android Auto API Endpoints

### What shipped

**3 files changed (commit 3c2d227 on master)**

- `api/app/routers/artists.py` — Fixed `GET /artists/{id}/top-tracks`: rewrote from ORM to raw SQL, replaced `albums.artist_id` filter with proper `album_artists` join (with fallback for albums that have no `album_artists` rows), bumped hardcoded limit of 10 to a configurable `?limit=` query param (default 25, ge=1, le=100).
- `api/app/routers/tracks.py` — Added `GET /tracks` endpoint: `sort=play_count` (only sort supported), configurable `?limit=` (default 50, ge=1, le=200), auth required, returns standard track shape (id, title, track_number, duration_ms, bitrate_kbps, format, play_count, album_id, album_title, artist_id, artist_name).
- `web/src/pages/ArtistPage.jsx` — Updated top-tracks query to pass `?limit=10`, keeping the web UI at 10 tracks while Auto gets 25.

### Key decisions

- **Fix top-tracks in place rather than add a new `/artists/{id}/tracks` endpoint** — original PRD had a new endpoint; user corrected it mid-session to fix the existing one. The `album_artists` join logic matches what `GET /artists/{id}/albums` already does (same fallback pattern).
- **Configurable limit on top-tracks** — web wants 10, Auto wants 25, so hardcoding either would break one caller. Query param with default 25 (Auto's value) keeps both happy.
- **`RANDOM()` tiebreaker dropped** — PostgreSQL rejects `RANDOM()` in `ORDER BY` with `SELECT DISTINCT`. Replaced with `t.id` for stable deterministic ordering. Random tiebreak in the original was cosmetic (the web shows 10 tracks; most libraries have play_count=0 for everything anyway).
- **`GET /tracks` always sorts by play_count DESC** — the `sort` query param is accepted but only `play_count` is implemented. No other sort is needed now; the param exists so Android Auto can explicitly declare its intent in the URL.

### Gotchas

- PostgreSQL does not allow `ORDER BY RANDOM()` (or any non-deterministic expression) combined with `SELECT DISTINCT` — the expression must appear in the select list. Use a subquery or drop the random tiebreaker.

### No DB/infra changes

No migrations. API rebuilt and redeployed twice during the session (build + `docker compose up -d api`). No nginx changes.
