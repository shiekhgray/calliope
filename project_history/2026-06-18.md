# 2026-06-18 — Vector Tuning: from DSP dead-ends to a pretrained embedding

Multi-day session (2026-06-16 → 06-18). Started with a quick frontend fix, then a
deep similarity-quality investigation that ended in a representation change.

## Shipped

### Radio Modes buttons were "missing" — stale Vite dev server (fix: restart)
The Radio Modes UI looked gone after the `radio` branch merged to master. Root cause
was **not** code or Docker images — the API already had the routes + migration 0014.
The 2-month-old Vite dev server (`calliope-web`) had served a **pre-merge cached

### Similarity quality investigation → PANNs audio embedding as the default space
The owner reported similar/radio mixing very different music (e.g. In Flames ≠ Evalyn).
A structured owner A/B on 11 known seed tracks drove the whole investigation. Findings,
in order:

1. **Diagnostics** (`scratch_vector_diag.py`): the 60-dim DSP vector behaves like ~14
   effective dims; the 4 "big blocks" (timbre/timbral-var/harmony/chord) are 2–3.5×
   internally redundant.
2. **Per-group balancing REFUTED**: equalizing group weights handed ~33% of the cosine
   to tempo+loudness+brightness (genre-agnostic) → a metal seed retrieved hyperpop.
   Worse, not better.
3. **Root cause of the regression**: migration 0010's 38→60 expansion diluted timbre
   from ~68% to ~43% of the vector by adding genre-blind chroma-variance/tonnetz/perceptual
   dims. Timbre-forward reweighting helped genre separation (metal vs pop margin ~2×) but
   timbre-only over-rotated (synthpop collapsed into metal).
4. **Key-invariance** (`track_vectors_ki`, migration 0015): chroma is absolute-pitch, so
   "harmony" was matching musical KEY (perceptually irrelevant w/o perfect pitch) instead
   of mode. Krumhansl-Schmuckler tonic rotation — derivable from stored chroma, no
   re-extraction. Helped artist-catalog cohesion (Men I Trust, Conjure One→Delerium) but
   couldn't fix timbral collisions (Lights↔Eluveitie) and slightly hurt same-key matches.
5. **The ceiling**: every DSP lever (balancing, timbre-forward, key-invariance, mean-forward)
   traded one error for another. Per-pair diagnosis showed the worst false match
   (Dragonfly→Kill Hannah Scream, #1) was driven by `timbral_variation` (MFCC *variance* =
   "busyness," near content-free). Conclusion: aggregate spectral stats fundamentally can't
   represent instrumentation/vocals/density/structure — a **representation** problem, not
   calibration.
6. **Fix: pretrained PANNs CNN14 audio embedding** (`track_vectors_embed`, migration 0016,
   2048-dim). CPU-only inference ~2.5s/track (no GPU; the i7-10700K is fine for one-time
   batch). Full library ~2.7h. **Decisive A/B win**: Dragonfly→Scream #1→#178, In Flames→
   Evalyn #4→#1775, Lights→Eluveitie #72→#3318; neighbor lists pull artists' own catalogs
   + genre/vocal-coherent matches, and the symphonic-metal leak on Morgan Page vanished.

   **Now the DEFAULT similarity space** for `/tracks/{id}/similar` and `/radio/next`
   (`?space=embed`). The DSP `standard`/`ki` spaces are kept as dev-only fallbacks via
   `?space=`. The 9 "Sound Matching" sliders were retired from the web user menu
   (`SimilarityWeightsModal.jsx` deleted); the `sim_weight_*` columns + endpoint were kept
   because MapPage's tuning panel (DSP Music Map) still uses them.

## Key decisions / tradeoffs
- **Parallel-table A/B harness**: rather than mutate the expensive `track_vectors`, each
  new representation is a separate table + a `space` selector (`SPACES` map +
  `load_embedding_matrix`). Zero-risk, droppable, and it turned out to be the exact rig for
  trying the embedding. KI was derivable from stored vectors (cheap); embed needed a full
  audio pass.
- **Embed has no weight-groups** → plain L2-normalized cosine, no z-score, no per-user
  weights. That's why the sliders were retired.
- **Owner's ear is ground truth** — no labeled dataset; all verdicts were owner A/B on seed
  tracks (notes were in the now-deleted `reactions.md`).

## Gotchas
- PANNs (`panns-inference`) imports `matplotlib.pyplot` at package load for unused plotting;
  stub `matplotlib` in `sys.modules` before importing to avoid the dep chain. Install with
  `--no-deps` + CPU torch index URL so it can't pull a CUDA torch. `wget` isn't in the
  slim image — pre-fetch the CNN14 checkpoint + label csv via `urllib` at build.
- Embed cosines sit in a compressed ~0.88–0.99 band (raw embedding) — rankings are clean;
  absolute scores aren't comparable to DSP cosines.

## DB / infra changes applied to production

## Session 2 — Embedded album art on import (Amazon)

Short, focused session. Investigated Amazon Music download cover art, then wired
automatic extraction into the import tooling.

### Context / discovery
- Sampled embedded art across 45 Amazon-sourced MP3s (3 album zips + 5 Kamino singles).
  All uniformly **600×600 JPEG** in the ID3 APIC frame; byte size varies only with JPEG
  quality (43 KB–269 KB), never resolution. So 600×600 is a safe assumption for Amazon art.
- Amazon zips ship **no cover file on disk** — and the scanner's `find_cover_art`
  (`api/scripts/scan.py:45`) only looks at on-disk `.jpg` files. Result: Amazon albums
  historically landed cover-less, and the owner had been manually hunting higher-res
  `Folder.jpg` covers after each import (confirmed: existing Kamino/In Flames albums carry
  882 KB–3.98 MB manual covers, far bigger than the 600×600 embedded art).

### Shipped — embedded-art extraction in BOTH importers
Owner chose "both importers" (not the scanner fallback option) — scope = new imports only.
- **`scripts/amazon_import.py`** (host CLI, driven by `/import-music`): added
  `extract_embedded_cover(bytes)` (ID3 APIC / MP4 'covr') + `has_cover_file(dir)` guard.
  Hooked into both the zip path (per album, from first track) and the loose-single path.
- **`api/app/routers/import_music.py`** (web `/import/upload`): mirrored `_extract_embedded_cover`
  + `_has_cover_file`; hooked into `_extract_amazon` (zip) and `_process_audio_single` (loose).
- Writes the embedded bytes to **`Folder.jpg`** (matches scanner priority 1) **only when the
  album dir has no `.jpg` yet** — never clobbers a manual higher-res cover. Idempotent on rescan.

### Key decisions / why
- **Both importers, not the scanner.** A scanner `find_cover_art` fallback would have been one
  place + retroactive backfill for all cover-less albums, but the owner wanted it confined to
  the import tools. Tradeoff accepted: logic lives in two spots (one helper each), existing
  cover-less albums are NOT backfilled.
- **Always `Folder.jpg` regardless of mime.** Scanner only matches `.jpg`; Amazon art is JPEG
  in practice, so a PNG edge case is served-by-bytes anyway.

### Verified end-to-end
- Helper extracts from both a zip track (53,680 B) and a library single (121,912 B).
- Real CLI zip import into throwaway root → `In Flames/Siren Charms/Folder.jpg` (53,680 B);
  **re-run = 0 rewrites** (idempotent, existing cover preserved). Loose single likewise wrote
  `GUNSHIP/.../Folder.jpg` (54,092 B). Both files `py_compile` clean.
- Traced the full web-upload chain: `ImportPage.handleUpload` → `/import/upload` (now extracts
  art) → on success `startScan()` → `/scanner/trigger` → `scan.py` (reads the just-written
  Folder.jpg) → indexer `/index` → `run_indexing()` → `build_embeddings()` (PANNs CNN14, the
  new default encoder; incremental, ~2.5s/track CPU) → `build_map()`. Art extraction completes
  before the scan starts, so the cover is picked up in the same pass.

### Gotchas / notes
- **Web router change requires an API image rebuild** to go live: `docker compose build api &&
  docker compose up -d api` (code is baked into the image). CLI script runs on host, no rebuild.
- `api/CLAUDE.md` Import Format Detection → Amazon bullet updated to document the embedded-art
  fallback.
