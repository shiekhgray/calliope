## Session 1

### PRD: Playlist Mosaic Banner

**Goal**: Design spec for a full-width hero banner of album art at the top of the
playlist detail page. No code written this session — PRD only.

**File**: `prd/playlist-mosaic-banner.md`

**Design decisions** (captured via interactive Q&A):

- **Placement**: Full-width hero above the playlist title/description/track list.
  Nothing else changes on the page — content is below as normal.
- **Height**: ~174px (3 rows of 56px cells + 3px gaps).
- **Background**: `linear-gradient(to right, #0e0e0e 0%, transparent 90%)` —
  dark on the left where art is dense, transparent on the right where it thins out.
  Empty cells just show the gradient.
- **Density gradient**: Fill probability per column = `1 - (c/C)^0.55` — convex
  curve, slow falloff on left, steep on right. Left ~40% near-fully packed, right
  ~20% nearly empty.
- **2×2 squares**: Albums with the most tracks on the playlist earn a 2×2 slot.
  Top 25% of unique albums (capped at 3) get promoted. Ties broken by playlist
  positional order (first occurrence).
- **Reactivity**: No session seeding — random state freshly sampled on each load.
  Different layout on each page visit (intentional).
- **Implementation**: Entirely client-side. No API changes. Component reads from
  the track list already present on the playlist detail page.
- **Each album appears exactly once** — duplicates suppressed in the packing loop.

**Key algorithm**: bin-packing left-to-right, large squares first. Active cell
matrix built by sampling density curve per column. Placed items rendered as CSS
grid cells with `grid-column/row: span 2` for 2×2 squares.

## Session 2

### Feature: Playlist Mosaic Banner

Implemented `web/src/components/PlaylistMosaicBanner.jsx` per the PRD written in Session 1. No API changes — entirely client-side.

**What ships:**
- Full-width 174px hero banner above the playlist title/tracks on PlaylistPage
- 3 rows × dynamic columns (56px cells, 3px gaps, `floor(windowWidth/59)` cols)
- Albums sorted by track-count frequency; top 25% (capped at 3) get 2×2 slots
- Background: `linear-gradient(to right, #0e0e0e 0%, transparent 90%)`
- Art fetched via `/calliope/api/albums/{id}/art`; broken art silently hidden via `onError`
- Banner placed as sibling before `.page` (outside padding) for true full-width

**Algorithm iterations:**
1. Initial: row-first scan + power curve `1 - x^0.55` → 3rd row always empty, sparse left
2. Fixed: switched to column-first scan → all 3 rows now fill; also switched curve to `exp(-4x)`
3. Fixed: curve upgraded to squared exponential `exp(-4x²)` → early columns near-certain (col 1 at 99% vs 85%), steep falloff after midpoint

**Key bug fixed — "tetris shuffle":**
`PlaylistPage` consumes `usePlayer()` whose context value rebuilds every second (audio progress ticks). Each rebuild caused `playlist.entries.map()` to create a new array reference → `useEffect([tracks])` fired → `Math.random()` → new layout → visual shuffle.

Fix: derive `albumSig` (sorted unique album IDs as a joined string) and use that as the effect dep instead of the `tracks` array. The layout only recomputes when the album composition actually changes. Use `tracksRef` to avoid stale closure on `tracks` inside the effect.

**CSS added:** `.mosaic-banner`, `.mosaic-banner img` in `index.css`

**No DB/infra changes.**
